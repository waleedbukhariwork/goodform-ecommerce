**`/email-verified` page (the landing after clicking the email link):**

The page uses `export const dynamic = "force-dynamic"` (always server-rendered) and reads the `error` param from `searchParams`. On refresh:

- **If verification succeeded:** Better Auth's `autoSignInAfterVerification: true` (in `identity.service.ts` line 73) set a session cookie when redirecting here. The `EmailVerified` component calls `useSession()` → `fetch("/api/auth/get-session")` with `credentials: "same-origin"`, so the HttpOnly session cookie persists across refresh. The user sees the same "Your email is confirmed" success screen and the 4-second auto-redirect to `/` re-triggers.
- **If verification failed (expired/invalid token):** Better Auth redirects to `/email-verified?error=TOKEN_EXPIRED` (or `INVALID_TOKEN`). The `error` param lives in the URL query string, so it survives refresh. The `verificationError()` function maps it to the friendly message and the "Back to your account" link is shown.

This page is **refresh-safe** — state comes from URL params + cookie, both of which persist.

**Resend link view (the verify step inside `AccountForm` on `/account`):**

All state lives in React `useState` (`email`, `linkSent`, `cooldown`, `resendCount`, `step`). On refresh:

- **All client-side state is lost** — the user is dropped back to the initial "Sign in or create an account" form with an empty email field. The client-side cooldown timer (a `setInterval` at `account-form.tsx` line 68) is gone.
- **What survives:** The server-side `MailThrottle` in PostgreSQL. It stores a salted SHA-256 hash of the email (never the raw address), enforced via a unique constraint on `(kind, email_hash, window_started_at)` in the `mail_send_attempts` table. The throttle is applied in `ResendMailSender.send()` → `throttle.claim()` **before** the Resend API call, so it's independent of browser state.
- **When the user re-enters their email:** `continueWithEmail()` calls `/api/v1/auth/account-state` (returns "unverified"), then `fetchCooldown()` calls `/api/v1/auth/mail-cooldown` which queries `MailThrottle.remaining()` from the database. The server returns the real remaining seconds, and the client re-syncs to it. If the user tries to send during cooldown, the server returns 429 `MAIL_COOLDOWN` and the client's `verificationLimited()` check (line 28) handles it gracefully.

So the resend link view **degrades gracefully** — UI state is lost but the server-side throttle is intact. The user has to re-enter their email, but the server correctly reports the remaining cooldown. The client-side timer is explicitly described in comments as cosmetic: *"The value is advisory: the throttle is enforced on the send path regardless"* (`mail-cooldown.controller.ts` line 9) and *"a refresh clears it and devtools bypasses it entirely, which leaves a paid provider's quota exposed to abuse"* (`mail-throttle.ts` line 19).

**Key design difference:** `/email-verified` is a standalone route built to be refresh-safe (you land here from an email click, not SPA navigation). The resend link view is a transient step in the account form — losing its state on refresh is acceptable because the server re-syncs the user to the correct cooldown immediately.
