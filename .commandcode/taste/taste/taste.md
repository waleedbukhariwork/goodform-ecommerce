# Taste
- Prefers analyzing the latest live code (source files) over documentation when investigating how something works — wants the real behavior of the codebase, not what docs say. Confidence: 0.9
- Prefers automation that fires on its own (tool hooks / lifecycle events) over anything that must be remembered and run manually; expects the agent to actually research a tool's capabilities before answering, not guess or fall back to a manual workaround. Confidence: 0.75
- Expects verification before building: prove a mechanism works first (canary test, fresh sessions to show it isn't session-local, written test report) before starting real work. Also repeatedly fires short labelled canary prompts ("CAPTURE TEST — <project>, <name>, new fresh session") in brand-new sessions and expects confirmation the mechanism actually fired, not just a description of it. Green local tests are not enough to declare something done — an integration stays "unverified" until the live test passes, and the failure gets investigated first. Confidence: 0.8
- Values honest, unedited records over tidy ones — keep dead ends, wrong turns, failed attempts, and full verbatim prompts/responses; no post-hoc summarising, cleanup, or deletion. Confidence: 0.7
- Wants agent transcripts captured to `.agent-logs/` at the repo root and committed alongside the code they produced (never gitignored), with interleaved commits so the real order of work is visible. Confidence: 0.55
- Git commits must never carry a `Co-authored-by` trailer or any other co-author line in the commit message. Confidence: 0.95
- When a preference is stated, expects it persisted as a repo-wide rule (e.g. an `AGENTS.md` rules file committed to the repo) so every future session and tool picks it up — not merely applied once in the current conversation. Confidence: 0.75
- Works in Command Code CLI (`cmd`) on Linux; project-level agent config lives under `.commandcode/` (`settings.json` hooks, `hooks/` scripts), and headless `cmd -p "..."` is used to spin up fresh sessions for testing. Confidence: 0.6
- Splits agent labour deliberately: a planning/architect agent (OpenAI Codex, run with escalated-permission approvals) does interpretation, architecture, product decisions, prompts and review, while Command Code does the implementation. Expects the planner to hand off precise, copy-ready implementation prompts rather than loose descriptions. Confidence: 0.65
- Wants the agent to behave like a principal engineer / solution architect: challenge weak assumptions, state tradeoffs explicitly, and prioritise practical delivery inside a hard time budget (plans must be proportional to the deadline, with milestones, buffer, an explicit feature-freeze point, and written scope-cut rules). Confidence: 0.75
- Plans before code, with an explicit approval gate: expects a first response that interprets the task and its delivery risks, asks at most ~5 high-impact clarifying questions, proposes a direction plus one recommended differentiator, and gives a prioritised feature table (user value, dependencies, effort, scope tier) and a stack/architecture recommendation with tradeoffs — and no implementation until the decision table is approved. Confidence: 0.8
- Prefers a smaller, coherent, fully-working product over a broad set of unfinished features; when scope must shrink, cut features first and never compromise the core user journey, authorization, data integrity, or deployment reliability. Confidence: 0.75
- When reporting a problem, expects the agent to investigate it to a root cause and come back with a recommended solution — not just restate the symptom or ask what to do. Confidence: 0.7
- Asks for a critical review of his own implementation (e.g. "analyze my implementation of X") and expects a real audit: what's strong plus concrete, ranked, actionable defects with fixes. Confidence: 0.7
- Communication style: brief explanations of decisions, assumptions and uncertainties stated openly, no exaggerated expertise claims or unsupported guarantees (don't promise to beat competitors — produce evidence instead), and never fabricate benchmarks, test results, deployment status, or completed work. Confidence: 0.9
- Judges work by evidence a reviewer can check: expects final deliverables to include a working deployment, reproducible repo setup, demo data/accounts, a concise architecture and scope write-up, verification evidence, known limitations, and a short demo script. Confidence: 0.65
- Demands professional, brand-matched UI/UX over browser defaults or generic error messages — wants Amazon-style flows and engineering practices (idempotency, retries, secure checkout) and explicitly rejects AI-generated design patterns ("AI slop"), preferring human-centered, senior-designer thinking. Confidence: 0.85
- Strongly deploy-first: constantly asks "deployed?", "deploy it", "deploy latest commit", and wants a single command that completes deployment; treats working deployment as a core deliverable, not an afterthought. Confidence: 0.9
- Insists on app-wide consistency: UI/UX patterns, button styling, and error states must be uniform everywhere in the app — no gaps, drifts, or inconsistencies anywhere. Confidence: 0.85
- Wants security-conscious but user-friendly errors: error messages must be helpful for non-secret issues without leaking sensitive information (e.g., distinguish between client-visible and secret server errors). Confidence: 0.8
- Specific UI/UX preferences: sticky navigation, browser tab favicon/icon, no em-dashes in browser tab titles, quantity visible in cart, 3D design where appropriate (especially mobile-friendly surfaces). Confidence: 0.75
- Prefers brief pre-action communication: asks to be informed ("let me know what you are gonna do") before major implementation steps begin, rather than being surprised mid-work. Confidence: 0.75
