# Commerce data and local observations

## Cart and reservations

The cart persists at most 20 distinct product/size lines per account. Each quantity is an integer from 1 through 10. Unknown fields are rejected. The optional `priceCents` input on a cart PUT is accepted only to demonstrate that client-supplied prices have no effect; it is never read by the cart service. Every cart response joins current catalog snapshots through the catalog's public capability and calculates integer-cent line and cart totals on the server. A checkout will re-read prices inside its transaction in the orders phase.

Inventory tracks physical on-hand and available units for each product and size. Reserving decreases available; consuming at checkout decreases on-hand; releasing increases available. The catalog seed inserts five units per variant only if no stock row exists, so rerunning it does not replenish sold or reserved units. A cart reservation lasts 15 minutes. The inventory repository sorts lines and updates each stock row only when `available >= requested quantity` inside one PostgreSQL transaction, then inserts the reservation line. Failure rolls back both stock decrements and the reservation group. A group and its lines are read only with a matching session owner. Expired active groups are released explicitly by `pnpm --filter @goodform/api db:release-reservations`. That command transitions status and increments stock in one transaction; rerunning it makes no further change. There is no background release timer.

## Phase 3 HTTP and database observations, 2026-09-29

Using two freshly signed-in accounts against the running local API and disposable PostgreSQL, both cart PUT requests returned 200 with a 3,900-cent server total after submitting `priceCents: 1`. Cart responses had `Cache-Control: private, no-store`. Quantities 0 and 11 and an unrecognized field each returned 400. The first account signed out, signed back in, and GET `/api/v1/cart` still returned its item and 3,900-cent total. An attempt to delete the other account's cart item returned 404.

For a size with exactly one available unit, two concurrent POST `/api/v1/reservations` requests returned one 201 and one 409 problem+json. PostgreSQL showed one active reservation group, one line, and zero available units. The other account's GET of the winner's reservation returned 404; the owner received 200 and `active`. After moving that disposable reservation's expiry into the past, the release command reported one release, then zero on a second run. Available stock went from zero to one, and the group became `released`. The demo stock row was then restored to five units. These are local observations; no checkout or payment was involved.

## Orders and transaction boundary

`TransactionRunner.run` passes one explicit Drizzle transaction handle to the cart and catalog price reads, inventory reservation consumption, and order writes. A reservation reduces `available`; order preparation reduces physical `on_hand` and changes the reservation to `consumed` in that same transaction. The order stores name, slug, image path, size, quantity, unit price and line total as immutable snapshots. The order GET reads only those snapshots. The domain status transition permits `payment_pending` to become `paid`, `failed` or `cancelled`; there is no client status update route. The Phase 4 `POST /api/v1/orders/prepare` route created a local pending order for HTTP proof; Phase 5 replaced it with the guarded Stripe checkout action.

## Phase 4 local observations, 2026-09-29

Migration and seed exited zero against disposable PostgreSQL. A cart with one 3,900-cent item reserved stock from `available=5,on_hand=5` to `4,5`. POST `/api/v1/orders/prepare` returned 201 with `payment_pending`, a 3,900-cent total and the line snapshot; stock became `4,4`. Supplying `status: paid` in the request returned 400. After temporarily changing the live product's name and price, the order GET still returned its original name and 3,900-cent price and total. The product row was restored. These are local observations; no Stripe session or payment occurred.

## Stripe TEST checkout and recovery

`POST /api/v1/checkout` requires an authenticated session, a reservation UUID and a client-generated UUID v4 `Idempotency-Key` header. PostgreSQL has a unique `(user_id, idempotency_key)` checkout record. A single transaction reserves the key, re-reads the cart and catalog price, consumes the reservation and physical stock, and writes the `payment_pending` order and immutable lines. The test-mode Stripe Checkout Session is created after this database transaction with SDK retries disabled and a Stripe idempotency key derived from the database attempt ID. This external API call cannot participate in a PostgreSQL transaction. A completed attempt stores the provider session ID and URL; a repeated client key returns the same stored URL. An uncertain provider response marks the attempt `uncertain`, retains the pending order and stock state, and does not call Stripe again automatically.

When an order first becomes `paid`, the same database transaction removes the purchased quantity of each order line from that owner's cart. A variant the shopper added after checkout keeps the extra quantity. A failed or cancelled checkout leaves the cart unchanged. Duplicate payment events do not remove the cart again. `GET /api/v1/orders` returns the owner's 50 most recent orders. Stripe still returns the browser to `/orders/:id?checkout=return` or `checkout=cancelled`; that page reconciles the stored Checkout Session once, because the redirect itself does not mark the order paid.

The separate `/api/stripe/webhook` Express route reads raw bytes before the JSON parser and checks `Stripe-Signature` with the official SDK. Only `livemode=false` events are accepted. Every successfully processed event ID is inserted into a primary-keyed PostgreSQL table in the same transaction as any order transition. Duplicates return 200 with `duplicate: true` and make no second change. For relevant checkout events the handler retrieves the current provider Checkout Session, checks the session ID, order reference, metadata, USD amount and test mode, then applies the current provider state. This current-state read lets later and out-of-order event deliveries converge. A paid browser redirect changes no order state. Failed or expired checkout restores consumed stock once. The authenticated `POST /api/v1/orders/:id/reconcile` operation retrieves the stored provider session and applies the same state mapping if a webhook was missed.

If a checkout attempt is `uncertain` or has no stored Stripe session ID, an operator must inspect Stripe test-mode sessions using the order reference and database attempt before deciding whether to attach a session, expire it, or restore stock. Do not initiate a second automatic provider request. Run `pnpm --filter @goodform/api db:release-reservations` for expired reservations that were never consumed. Configure Stripe test key and webhook secret files through the optional `infra/compose.stripe-test.yml` release overlay by setting `ENABLE_STRIPE_TEST=true` in the private release environment file; the release dry-run checks both mounted files. The base release continues with checkout unavailable when no Stripe credentials are configured.

## Phase 5 local observations and unverified boundary, 2026-09-29

No Stripe account test key or real webhook secret was injected. The payment migration and seed exited zero. A locally generated verifier secret, used only for a controlled HTTP signature probe, produced 400 problem+json for an invalid signature. A locally signed synthetic event returned 200 with `duplicate: false`, then 200 with `duplicate: true` for the same event ID; both responses used `private, no-store`. This proves the local raw-body signature and database duplicate path, not actual Stripe delivery or payment. A checkout request without `Idempotency-Key` returned 400. With a valid key and no account key it returned 503 problem+json and a request ID; the reservation remained active. Real Checkout Session creation, provider retrieval, paid/failed webhook transitions, and reconciliation remain unverified until Stripe test credentials and delivery are available.

A direct local PostgreSQL limiter probe, after moving its disposable window into the past, observed counts 1 through 5 allowed and counts 6 and 7 denied. This verifies the database rule locally; the full HTTP checkout rate-limit path is pending real Stripe test credentials.
